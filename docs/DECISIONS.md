# DECISIONS

## ADR-1：全栈 monorepo（Hono 单进程）而非纯前端聚合
- 日期：2026-11-12
- 状态：已采纳
- 背景（遇到了什么问题）：源站（hanime1 等）无官方 API，浏览器直连受跨域与防盗链限制，HTML 解析与 m3u8 代理只能在服务端做；同时希望一个进程部署完事。
- 考虑过的方案：① LibreTV 式纯静态前端 + iframe 嵌源站播放页；② LunaTV/MoonTV（Next.js 全栈）；③ OrionTV（React Native tvOS 原生应用）；④ pnpm monorepo：Hono API + React SPA 单进程。
- 决策：方案④，按 node-monorepo 路线落地。
- 为什么选这个：源适配必须服务端（②也满足，但 Next.js 运行时对本项目偏重）；单进程 `node dist/index.js` 自包含部署，SQLite 零配置；前端构建产物直接被 server 托管，无跨域。
- 为什么不选其他：①无法归一化数据、界面不可控；②框架耦合与运维成本高于一个 Hono；③原生应用无法以 Web 形式在电视浏览器/投屏使用。
- 后果：开发期需同时起两个进程（concurrently 已编排）；生产只需一个端口（11408）。
- 何时重新审视：出现多用户/公网部署诉求，或需要 SSR 时。

## ADR-2：源接口化——SourceAdapter 统一契约
- 日期：2026-11-12
- 状态：已采纳
- 背景（遇到了什么问题）：目标是聚合多个异构源站（首个 hanime1.me），各站列表/搜索/详情/播放地址结构完全不同，前端不能为每个源写一套。
- 考虑过的方案：① 每源一套前端页面；② CMS 采集站 JSON 当作唯一源格式（LibreTV/LunaTV 系做法）；③ 自定义 SourceAdapter 契约（list/search/detail），归一化为 VideoSummary/VideoDetail/Page。
- 决策：方案③，契约落在 `packages/shared/src/types.ts`，server 侧维护 adapter 注册表。
- 为什么选这个：hanime1 不是 CMS 采集站，②覆盖不了；契约足够小（三个方法），任何能被抓取的站点都能实现。
- 为什么不选其他：①前端复杂度随源数线性增长；②绑定采集站生态，非采集源接不进来。
- 后果：新增源 = 写一个 adapter + 注册，前端零改动；源站改版只需改对应 adapter。
- 何时重新审视：出现源需要「登录态/付费解锁」或「字幕轨道」等契约未覆盖的能力时。

## ADR-3：tvOS 风格自建（Web）而非复用原生方案
- 日期：2026-11-12
- 状态：已采纳
- 背景（遇到了什么问题）：产品要求 Apple TV 视觉与遥控器/方向键操作；社区只有原生 tvOS 实现（OrionTV，React Native tvOS + Expo），没有可复用的 Web 版。
- 考虑过的方案：① 直接用 OrionTV（原生双端）；② 拿 LunaTV 界面改皮；③ React SPA 自建 tvOS 视觉语言 + 空间导航库（`@norigintech/norigin-spatial-navigation`）。
- 决策：方案③。
- 为什么选这个：部署形态必须是 Web（自托管单进程）；空间导航库解决焦点引擎这个最难的骨架问题，视觉层（大图卡片、顶部 tab、毛玻璃）用 Tailwind + shadcn 自建可控。
- 为什么不选其他：①无法 Web 部署，且其后端假设是 LunaTV 系；②界面结构非焦点优先，改造成本高于自建。
- 后果：tvOS 视觉细节需自行打磨；焦点交互要作为验收标准写进 spec。
- 何时重新审视：若未来需要 tvOS/Android TV 原生端，OrionTV 可作为参考实现重新评估。

## ADR-4：双播模式——CDN 直放优先，后端下载转本地为兜底
- 日期：2026-11-12
- 状态：已采纳
- 背景（遇到了什么问题）：源站播放地址是带过期时间的签名直链（hanime1 约一天有效），且受防盗链/CORS 与网络可达性影响；电视端不能每次都依赖第三方 CDN。
- 考虑过的方案：① 一律经服务端流代理直放；② 一律先下载再播；③ 双播模式：默认 CDN 直放（经服务端 Range 代理，不落盘），用户可对任意视频「下载到本地」，之后优先本地。
- 决策：方案③。
- 为什么选这个：直放不占磁盘、即点即看，适合「能看就行」；下载适合收藏与离线，且源站删稿后仍可看。两者共用同一个媒体来源解析出口，前端只切一个 mode。
- 为什么不选其他：①所有流量过本机，磁盘虽省但带宽与 CPU 全压在本机，且签名过期后无法重播旧片；②每个视频都要等下载完，违背电视端浏览习惯。
- 后果：需要下载任务队列（单并发）、本地库（SQLite）、磁盘配额与清理策略；离线模式需要全局开关，离线下所有源站请求短路。
- 何时重新审视：若源站开始提供官方 API/下载授权，或本地存储成本成为主要约束。

## ADR-5：上游传输层改用 curl 子进程，绕开 Cloudflare 的 TLS 指纹判定
- 日期：2026-11-12
- 状态：已采纳
- 背景（遇到了什么问题）：hanime1 由 Cloudflare 防护。实测即使携带浏览器中获取的有效 `cf_clearance`，Node/undici fetch 仍返回 WAF ban（`Attention Required`），而同一 IP、同一 Cookie 下系统 curl 返回 200。二分定位到两个判定维度：TLS ClientHello 指纹，以及请求头名的原始大小写（小写的 `user-agent:`/`cookie:` 直接触发 ban）。
- 考虑过的方案：① 用 curl-impersonate 原生库绑定；② 使用 Puppeteer/Playwright 无头浏览器取页面；③ Node 内置 fetch + 自定义 TLS 指纹（Node 无此能力）；④ 系统 curl 子进程 + 头名规范化。
- 决策：方案④。`sources/curl.ts` 封装 curl 调用（`-4 --resolve` 直连 IPv4、`-r` 透传 Range、临时文件收集大响应），`http.ts` 保留缓存/频控/语义映射。
- 为什么选这个：零额外原生依赖、跨平台可用；实测连续请求稳定 200；保留 Node 层对缓存与错误映射的控制。
- 为什么不选其他：①需要在部署机编译原生绑定，跨平台维护成本高；②常驻浏览器实例内存开销大，电视端低配部署机吃不消；③Node 标准 TLS 栈无法伪装 JA3。
- 后果：部署机必须装有 curl（Windows 10+/主流 Linux 自带）；每次请求多一个进程开销（配合 60s HTML 缓存与 400ms 频控可接受）。
- 何时重新审视：若部署环境不保证 curl，可回退为 curl-impersonate 绑定；若源站提供官方 API 则整体删除该模块。

## ADR-6：DNS 污染应对——DoH 自解析 + --resolve 直连 IPv4
- 日期：2026-11-12
- 状态：已采纳
- 背景（遇到了什么问题）：本机系统 DNS 对 hanime1.me 返回被污染的地址（Facebook 段 / 黑洞 IP），IPv6 出口不可达；而 DoH 端点本身在有网时可能被墙或被污染（阿里 DoH 亦返回污染结果）。
- 考虑过的方案：① 依赖系统 hosts；② 全量走代理；③ 可配置多条 DoH 端点 + 可选「DoH 走本机代理、站点直连」拆分；④ 环境变量钉死 IP。
- 决策：方案③+④：`resolveIpv4` 依次尝试 `1.1.1.1` / `doh.pub` / `dns.google`（可经 `HANIME1_DNS_PROXY` 单独代理），结果以 `curl --resolve host:443:ip` 注入；另提供 `HANIME1_RESOLVE` 直接钉死 IP。
- 为什么选这个：站点访问经代理时 CF 会给挑战页（Just a moment），因此必须直连；而解析必须走可信 DoH。两项分离后实测稳定 200。
- 为什么不选其他：①维护手工 hosts 无法跟随 CDN 漂移；②全量代理被 CF 挑战拦截。
- 后果：多一个运行时配置面（DNS 代理）；跨境部署时通常无需任何配置即可直连。
- 何时重新审视：源站迁出 Cloudflare，或本地网络环境变化（如启用透明代理/DoH）。

## ADR-5：Aerial 观感——纯 CSS 背景轮播 + 自建页面转场
- 日期：2026-11-24
- 状态：已采纳
- 背景（遇到了什么问题）：首页有壁纸缓推，但内页是纯黑，硬切之后「进门就掉档」；焦点反馈只是 200ms 的 `transition-all` 加硬描边，缺 tvOS 的浮起感。
- 考虑过的方案：① 引入 framer-motion 做转场编排；② View Transitions API；③ 纯 CSS keyframes + 一个自建 PageStage 容器 + norigin 焦点上下文。
- 决策：方案③。背景 6 张 Unsplash 空镜，排程全写在 CSS（按层的 `--slot` 推导延迟），JS 只做预加载与 144s 一轮后的重挂。
- 为什么选这个：转场必须与 norigin 的焦点注册、`setFocus` 时机同步，VT 的快照模型对不齐，且 Firefox 支持不全要维护两套降级；framer-motion 对这类固定节奏的动画是多余依赖。
- 为什么不选其他：①多一层运行时依赖，且与空间导航的焦点时序仍需手工对齐；②快照期间旧 DOM 仍可导航，需要手动 pause/resume，降级路径等于自建一套。
- 后果：退场页必须 `focusable=false`，且转场容器里「退场层先渲染、入场层后渲染」的顺序不能调换（同名 focusKey 由后注册者覆盖）；内页背景模糊上限 3px，全屏大图 blur 是掉帧主因。
- 何时重新审视：若 norigin 不再需要与 DOM 同步，或 View Transitions 在各主流浏览器稳定后，可评估替换 PageStage。

## ADR-7：线索分两层——发现规则（线索）与调度单元（采集器），去重落到全局作品台账
- 日期：2026-11-25
- 状态：已采纳
- 背景（遇到了什么问题）：上一版的「线索」把发现参数（关键词 / 分区 / 发布者）和调度参数（巡检间隔）揉在一张表里，每次只抓第 1 页、首轮只补最新 3 条；去重只有「线索 × 作品」一级，跨线索只靠下载队列的内存判断，重启即失效，既没法表达「分区 + 关键词」的组合，也没法控制采集多少。
- 考虑过的方案：① 在旧表上加字段（分区、关键词、页数），间隔仍挂在每条线索上；② 两层模型：线索只管「发现什么」，采集器管「几条线索的并集 + 触发时机」，另建全局作品台账；③ 完全交给下载队列去重。
- 决策：方案②。`clues` 存发现参数与数量（前 N 页 / 全部），`fetchers` 存触发时机（手动 / 1H / 1D / 1W / 1M）与清晰度；`clue_seen` 记每条线索自己的扫描记忆，`works(source, video_id)` 是全局台账，决定是否入队并跟踪入库状态。
- 为什么选这个：用户要的是「多线索并集 + 交叉去重」；并集天然属于调度层，发现参数属于规则层，分开后新建线索只需选一个采集器。台账带状态后，失败补投、用户取消、删库都能区分，而内存队列做不到跨重启。
- 为什么不选其他：①间隔挂在每条线索上，就无法让一组线索共享触发节奏，页数也只能一律；③队列是内存态，重启即忘，失败与取消也分不清。
- 后果：一次结构升级（`subscriptions → clues`、`subscription_seen → clue_seen`）必须在单个事务里完成并留 `forager.db.bak`；「全部」必须增量早停，否则每次巡检都会翻几百页；补投次数只记失败（不记入队），因为重启会清空内存队列。
- 何时重新审视：若需要一条线索同时属于多个采集器，或需要按线索粒度设置触发。

## ADR-8：出口统一走 mihomo（Clash Meta），应用自带的 DoH 直连退为回退路径
- 日期：2026-11-25
- 状态：已采纳
- 背景（遇到了什么问题）：各源各配代理（`HANIME1_PROXY` / `PIXIV_PROXY`），Pixiv 不走代理基本不通，Hanime1 偶尔被 Cloudflare 判定需要直连；用户希望「应用内流量统一走一个节点」，不想为每个源分别维护代理。
- 考虑过的方案：① 各源继续各自配代理；② 应用内置 Clash 内核（编译成本高、跨平台麻烦）；③ compose 里加官方 mihomo 容器，应用只认 `http://mihomo:7890`，分流写在该容器的配置里；④ 用现成的代理客户端进程，不做容器。
- 决策：方案③。订阅地址写在 `.env` 的 `CLASH_SUBSCRIBE_URL`，入口脚本把它渲染进 `clash/config.example.yaml`；没填就渲染 `clash/config.direct.yaml`（全部直连 + DoH），保证没配订阅也能出网。应用侧 `FORAGER_PROXY` 默认指向 mihomo，各源单独配置时仍优先。
- 为什么选这个：应用不需要理解节点、分流、DNS，只认一个 HTTP 代理；订阅格式由 mihomo 原生支持（clash YAML、链接列表、base64）；容器之间用服务名即可互通，不必把无认证代理端口暴露到宿主机。
- 为什么不选其他：①每个源各配一份，换订阅要改多处；②把 Clash 内核塞进 Python 服务既重又不稳；④绕开容器编排，部署机得另装服务。
- 后果：设了代理后应用自己的 DoH 与 `--resolve` 不生效，解析交给 mihomo；Hanime1 默认直连（ADR-6 的挑战页问题），其余流量走订阅节点；订阅地址填错时 mihomo 起不来，靠 restart 策略重试并在日志里说明。
- 过程记录：接 mihomo 的起因之一是排查「`裏番` 分区解析为空」。最终查明与出口无关——该分区页面用的是另一套紧凑卡模板（见 `sources/hanime1.py` 的选择器表），任何出口下都解析得到 41 条。
- 何时重新审视：若源站能直连且稳定（可把 `FORAGER_PROXY` 清空回到应用自带直连），或需要按域名给控制器/面板加认证时。

## ADR-9：元信息产物——库内快照 + 媒体旁的 `.info.json` / `.nfo` / 海报
- 日期：2026-11-25
- 状态：已采纳
- 背景（遇到了什么问题）：入库只在 `library.meta_json` 存了详情页的原始返回，里面有会过期的签名直链与「当时的相关推荐」；详情页上的简介、上传日期、观看数、时长根本没解析。库文件与数据库绑死，媒体目录没法独立使用。
- 考虑过的方案：① 只存库内快照；② 快照 + 同名 `.info.json`；③ 快照 + `.nfo` + 海报（Kodi / Emby / Jellyfin 可读）。
- 决策：方案③。入库前把详情投影成「页面元信息」（剔除 `streamUrl / streamProxyUrl / qualities / related`）；媒体旁写 `<stem>.info.json`（无损快照），视频类再写 `<stem>.nfo`；新下载的海报直接落在 `<stem>-poster.<ext>`，`cover_file` 指向它（旧条目的 `covers/` 路径继续有效）。
- 为什么选这个：训练员要「除了媒体本身，还有页面携带的媒体元信息」——`.info.json` 让归档自解释，`.nfo` 与海报让媒体库扫一眼就能用，三者都从同一份投影生成，互不漂移。
- 为什么不选其他：①库丢了文件就成了裸 mp4；②媒体库读不到，需要另外刮削。
- 后果：删除与换清晰度重下都要连带清理这些文件；`.nfo` 用 ElementTree 生成并剔除 XML 非法字符；存量条目没有副产物（不回填）。
- 何时重新审视：若需要 TV 剧集形态的 NFO（当前一律按 movie 写），或需要为图片类条目生成其它元信息格式。

## ADR-10：统一 Focus Manager，视觉与交互同源
- 日期：2026-11-26
- 状态：已采纳
- 背景（遇到了什么问题）：tvOS 的视觉（弹簧放大、描边、三层视差）与交互（方向键焦点、货架跟随滚动、焦点恢复）此前分散在各组件里：每张卡自己 `onFocus` + `scrollIntoView`，每页自己 `setFocus` + `setTimeout` 兜底。鼠标移入只亮视觉、不动焦点，遥测式操作与鼠标操作各指一边；滚动、卸载、页面切换时焦点常常丢到 body。
- 考虑过的方案：① 维持各组件自理；② 换一套空间导航库；③ 在 norigin 之上建一层 Focus Manager，所有页面/组件只声明意图。
- 决策：方案③（`apps/web/src/lib/focus.ts` + `lib/norigin.ts`）。职责划分：Focusable 只上报「谁拿到了焦点」（实例 key + 语义 key）；Manager 统一负责——焦点记忆与恢复（同货架相邻卡 → 上一站 → 页面落脚点 → 第一个）、横向货架跟随滚动（滚容器、不滚窗口）、页面落脚点与记忆（含按「第几个货架第几张卡」的位置指纹）、Tab 与方向键的统一、鼠标悬停时把空间焦点移过来。
- 为什么选这个：norigin 的注册表以 key 为准，React 在页面切换/列表重排时会复用实例，同一 key 指向旧节点会让 `setFocus` 静默失效（实测首页与每次页面切换都会丢焦点）。Manager 让 Focusable 每次挂载用新的实例 key、DOM 上保留语义 key 做映射，从根上避开这个问题；同时把散落各处的焦点时序收成一处，页面只声明「落脚点」。
- 后果：页面的焦点行为要按约定实现——登录后的二级页必须有落脚点或返回键；列表刷新后焦点由 Manager 轮询恢复；`scrollIntoView` 不再出现在业务代码里。鼠标用户与遥控器用户共享同一焦点状态，最后一个动过的元素始终是焦点。
- 何时重新审视：React 对空间导航原生支持（实例与注册表一一对应、卸载即注销）之后，可以裁掉实例 key 这一层。

## ADR-11：首页背景图不入库，首次运行由服务端拉进本地库
- 日期：2026-11-26
- 状态：已采纳
- 背景（遇到了什么问题）：6 张 2400×1350 的 Unsplash 背景图（约 3MB）直接放在前端 `public/`，既进仓库又进构建产物；仓库本身并不需要这些装饰性素材，首次使用也要先等它们加载。
- 考虑过的方案：① 继续放仓库；② 前端直接请求 Unsplash；③ 服务端维护图片清单，首次运行时经统一出口拉到本地库，前端只取就绪清单。
- 决策：方案③。清单（slug + Unsplash 图片 ID）是服务端常量 `forager/wallpapers.py`，文件落在 `<data>/media/wallpapers/`；启动后台补拉（不阻塞服务），`GET /api/wallpapers/index` 返回就绪权重，`GET /api/wallpapers/<slug>.jpg` 直接出文件；前端只预解码下一张，首张解码完才整层淡入，缺图时只留深色底，主体内容不等图片。
- 为什么选这个：背景只是装饰，和封面图一样属于「本地库里的资源」；走服务端统一出口（mihomo）与其它出网请求同一条路径，登录保护也与业务接口一致。
- 为什么不选其他：①仓库与镜像白白变大，每次构建都要搬运；②绕开统一出口，离线/受限网络下不可控，且未登录也能拉。
- 后果：全新部署的最初几分钟背景可能还是深色底（后台下载中）；删除 `data/media/wallpapers/` 即可重新拉取；离线环境不会自动获得背景，但不影响任何功能。
- 何时重新审视：若需要用户自定义背景（上传/本地路径），应扩展为设置项而不是继续用内置清单。
